# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A one-page Astro marketing/news site for "TVBS TECH" (`src/pages/index.astro`), built from stacked section components rather than a scaffold. Default page language is `zh-Hant` (Traditional Chinese), set in `src/layouts/Layout.astro`. Package manager is **pnpm** (see `pnpm-lock.yaml`, `pnpm-workspace.yaml`); do not use npm/yarn commands or lockfiles.

## Commands

- `pnpm install` — install dependencies
- `pnpm dev` — start the Astro dev server
- `pnpm build` — build for production (outputs to `dist/`)
- `pnpm preview` — preview the production build locally
- `pnpm start` — run the built SSR server from `dist/server/entry.mjs` (what the Docker image runs)

There is no test suite, linter, or formatter configured.

## Architecture

- `src/pages/index.astro` is the homepage. It composes the page purely by importing and stacking section components from `src/components/index/` (Hero, New, Issue, Video, Crossover, Tech, Experts, Publications, EditorPick, TechLeaders, Partners) inside `<Layout>`.
- Other routes: `src/pages/[category].astro` (category listing page — `/tech`, `/money`; 404s via `Astro.rewrite('/404')` for any segment not in `CATEGORY_META`), `src/pages/[category]/[id].astro` (article detail page, `id` is `news_article_id`), `experts.astro` (expert/author listing page), `experts/[slug].astro` (per-expert detail page), and `404.astro`. All of these are plain SSR dynamic routes (`output: 'server'`) reading `Astro.params` directly at request time — none use `getStaticPaths`/prerendering (see "Dynamic routes" below for why that matters).
- `src/pages/api/*.ts` are server-only proxy endpoints (`export const prerender = false`) — e.g. `category-articles.ts`, `expert-articles.ts` — that front-end `<script>` "load more" pagination calls instead of hitting Strapi directly, since `STRAPI_API_TOKEN` only exists server-side.
- `src/lib/*.ts` holds fetch/formatting logic shared between pages and components (not just homepage sections): `articleDetail.ts`/`categoryArticles.ts`/`expertArticles.ts` (Strapi `article-libs` fetchers, one per call-site shape), `articleLink.ts` (`resolveArticleLink` — internal `/{category}/{news_article_id}` vs. external URL), `articleSummary.ts` (`resolveSummary` — prefer `news_summary` over a truncated fallback), `articleImage.ts` (`resolveArticleImage` — see CMS section below). Components still each redeclare their own slice of the Strapi response shape as a local `interface`; only the derived logic is centralized here.
- `src/layouts/Layout.astro` provides the HTML shell (meta tags, `<Header>`/`<Footer>`, `<slot />`), takes `title`/`description`/`keywords`/`ogTitle`/`ogImage`/`jsonLd` props, and embeds Google Tag Manager site-wide (`GTM_ID` env var) plus `history.scrollRestoration = 'manual'` (needed so the browser's own scroll-position restore doesn't fight the anchor-scroll logic described below). Pages build their own `jsonLd` object (`Organization`/`WebSite` graph on the homepage, `CollectionPage` on category pages, `NewsArticle` on article pages) and pass it through for the `<script type="application/ld+json">` tag.
- Each section component in `src/components/index/*.astro` has a matching stylesheet in `src/styles/components/index/*.css`, imported directly in that component's frontmatter (e.g. `import '../../styles/components/index/hero.css';`). `src/components/article/*.astro` (Adult, Share, ArticleContent, ArticleMore — used by the article detail page) follow the same pattern under `src/styles/components/article/*.css`. Non-homepage pages follow the same one-CSS-file-per-page convention under `src/styles/pages/*.css` (e.g. `category.css`, `experts.css`, `expert-detail.css`, `not-found.css`), scoped under a page-specific `#id` wrapper. Styles are plain global CSS, not Astro scoped `<style>` blocks — class names must stay unique enough to not collide across sections/pages.
- `src/styles/global.css` holds shared layout primitives and utility classes reused across sections: `.frameBox`/`.inBox` (outer/inner width containers with breakpoints at 1599/1279/1023/767/449px), `.newslist`/`.newslist.type2` (article list layouts), `.more` (CTA button), `.breadcrumbs` (`首頁 | 分類` style trail), `.itemTitle`/`.animLabel` (section title + entrance animation), `.statusIcon` (hover icon overlay), and `.pc`/`.mobile` visibility toggles (breakpoint at 1023px). Reuse these instead of re-implementing equivalent styles per section/page.
- Section anchor IDs (e.g. `#new`, `#spotlight`, `#video`, `#crossover`, `#experts`, `#publications`, `#collaboration`) match `Header.astro`'s nav links; keep them in sync when adding/renaming sections.
- Client-side behavior (nav scroll-based light/dark theming via `data-nav="dark"|"light"` on sections, smooth-scroll-to-anchor easing, mobile burger/submenu toggles) lives in inline `<script>` blocks in `Header.astro`, written in vanilla TypeScript — no framework/store is used for interactivity. Non-homepage pages participate in the same header theming by setting `data-nav="dark"|"light"` on their top-level `<section>`s (the header is always the plain white/black "top" state at scroll position 0 on every page, regardless of what's underneath — this is intentional site-wide behavior, not a bug).
- `public/` holds all static assets (images, SVG icons) referenced by absolute path (e.g. `/main-view-01.jpg`); there's no image import pipeline for these. Check for an existing asset (and its `-blue`/`-w`/etc. color-variant siblings) before downloading a fresh copy from Figma — e.g. `deco-upper.svg`/`deco-upper-blue.svg`/`deco-upper-w.svg` are the same shape in different fills, matching the pattern of an unsuffixed default plus color-suffixed variants.
- `src/data/*.ts` holds content shared across multiple pages (e.g. `experts.ts`, used by both `experts.astro` and `experts/[slug].astro`) so listing and detail pages stay in sync instead of duplicating arrays. Prefer this over a page-local `const` array once more than one route needs the same data.
- `astro.config.mjs` — `output: 'server'` with the `@astrojs/node` adapter in `standalone` mode; the site is SSR, not static. `pnpm build` produces `dist/server/entry.mjs`, run via `pnpm start` (or `node ./dist/server/entry.mjs`, as the Dockerfile does). Deploys as a Docker image (multi-stage `Dockerfile`, pnpm frozen-lockfile install, listens on `HOST=0.0.0.0`/`PORT=4321`).
- `tsconfig.json` — extends `astro/tsconfigs/strict`.

## CI/CD

- `.github/workflows/ci.yml` runs on every PR to `main`: install (`pnpm install --frozen-lockfile`) then `pnpm build`. That build is the only automated gate — there's no test or lint step to fail alongside it.
- `.github/workflows/deploy_testing.yml` triggers automatically on every push to `main` (excluding docs-only changes): builds a multi-arch Docker image, pushes it to ECR, and updates the `web-tech/overlays/testing/` kustomize values file in the separate `ops-tech` repo — i.e. **pushing to `main` immediately deploys to the testing environment**, not a no-op.
- `.github/workflows/deploy_production.yaml` is manual (`workflow_dispatch` with a `deploy_tag` input tied to a commit on `main`) and updates `web-tech/overlays/production/` instead — production deploys are a deliberate separate step, never automatic.

## CMS data (Strapi)

- Every section/page fetches live content from a headless Strapi instance at request time, directly in the component/page's frontmatter (or via a `src/lib/*.ts` helper) — `Header.astro` (nav), `Hero.astro`, `New.astro`, `Issue.astro`, `Video.astro`, `TechLeaders.astro`, `Crossover.astro`, `Tech.astro`, `Experts.astro`, `Publications.astro`, `EditorPick.astro`, `Partners.astro`, `[category].astro`/`[category]/[id].astro` (via `categoryArticles.ts`/`articleDetail.ts`), and `experts.astro`/`experts/[slug].astro` (via `expertArticles.ts`). Check whether a section actually fetches (`grep STRAPI_URL`) before assuming it's wired up if this list changes again.
- The pattern for a wired-up section: `fetch(\`${STRAPI_URL}/api/...\`, { headers: { Authorization: \`Bearer ${STRAPI_API_TOKEN}\` } })` wrapped in try/catch, falling back to an empty array/null on any failure (network error or non-OK response) so the page still renders. `STRAPI_URL`/`STRAPI_API_TOKEN` are imported from `astro:env/server` (declared in `astro.config.mjs`'s `env.schema` with `context: 'server', access: 'secret'`) rather than `import.meta.env` — Vite statically inlines `import.meta.env.*` at build time, which would have baked these into the Docker image as `undefined` since the K8s deployment (`ops-tech`) only injects them via ConfigMap/Secret at container start, after the image is already built. `access: 'secret'` makes Astro re-read the value from `process.env` on every request instead. In dev, values still come from `.env` (gitignored, not committed — no `.env.example` exists).
- Strapi's REST response shape is mapped into a local, section-specific TS interface (e.g. `TechTitan`, `HeroCard`, `MediaItem`) before rendering; raw Strapi field names follow a `<entity>_<field>` convention (`news_title`, `news_content_html`, `media_url`, `tech_titan_name`, …). There is no shared type module for these — each component redeclares its own interface for the slice of the response it uses — but the derived-value logic (summary/link/image resolution) is centralized in `src/lib/*.ts`, see below.
- `article-libs` has a `news_summary` field (optional, filled by content managers) — pass it through `resolveSummary()` from `src/lib/articleSummary.ts`, which prefers it and only falls back to a client-truncated `news_content_html` (each component keeps its own local `stripHtml()` since truncation length varies per layout) when it's empty.
- Every article list/card's main image goes through `resolveArticleImage()` in `src/lib/articleImage.ts`: `news_image` (a Media/upload field on `article-libs`, populated as an array — `[{ url }]`) wins when non-empty; only when it's empty does it fall back to `news_featured_image_url` (the plain external URL string scraped from the TVBS origin site). Since `news_image` is a relation, fetching it needs `populate[news_image][fields][0]=url` in the query (`fields[]` alone only selects scalar attributes) — see `Tech.astro`/`Hero.astro`/`New.astro`/`EditorPick.astro` for the populate shape at different nesting depths (flat list vs. dynamic-zone `on[...]` fragment vs. `s1_tech_zone`'s nested `articles` relation).
- Image URLs from Strapi may be relative (media-library uploads) or absolute (external hotlinks); prefix relative ones with `STRAPI_URL` before use (see `resolveArticleImage()`/`TechLeaders.astro`'s `image` logic) and always keep a static `public/` asset as the fallback when a field is null.

## Strapi response caching

Every Strapi fetch site listed above goes through `cachedFetchJson()` in `src/lib/fetchCache.ts` instead of a bare `fetch()` — before this, every request re-fetched Strapi live with zero caching anywhere (no CDN in front of the ALB, no nginx `proxy_cache` in the `ops-tech` sidecar, no app-level cache), and the homepage alone made 12 sequential Strapi round-trips per page load (`Header.astro`'s nav plus all 11 section components).

- **Two TTL tiers**, exported as `CACHE_TTL.NEWS` (3 min) and `CACHE_TTL.NAV` (10 min) from `fetchCache.ts`:
  - `NEWS` — anything that's an automatic "latest N articles" query (`Crossover.astro`, `Tech.astro`, `Issue.astro`, `categoryArticles.ts`, `expertArticles.ts`, `experts.astro`'s per-author `fetchLatestArticles`) — readers expect a news site's "latest" lists to reflect a just-published article within a few minutes, so this tier stays short.
  - `NAV` — everything else: `Header.astro`'s nav, single-article/single-expert detail lookups (`articleDetail.ts`), and every section whose content comes from a human manually picking/relating entries in the CMS ("套版" — `Hero.astro`, `New.astro`'s `s1_tech_zone`, `TechLeaders.astro`, `EditorPick.astro`, `Publications.astro`, `Experts.astro`'s `s5_author_column`, `Partners.astro`, plus the `authors` list fetch in `experts.astro`/`experts/[slug].astro`). These only change when someone edits content in the admin panel, so a longer TTL is free — it's not a "how fresh does this need to be" tradeoff so much as "how long until an admin's edit shows up," and 10 minutes is an acceptable wait for that.
  - When wiring a new fetch site, pick whichever tier matches — don't invent a third TTL without a reason; the whole point was to keep this to two easy-to-reason-about numbers.
- **Dev is always cache-free.** `cachedFetchJson()` checks `import.meta.env.DEV` (true under `astro dev`, false in an `astro build` output — this is a build-time constant, not read from an env var) and bypasses the cache map entirely in dev, so local development always sees the latest Strapi data. Caching only activates in the built app that `pnpm start`/the Docker image runs.
- **The cache is in-process memory** (`Map<url, {expires, data}>`), keyed on the full request URL. This means it's per-pod — each K8s replica keeps its own cache and they don't share entries — and it's cleared on every deploy/restart. That's a deliberate tradeoff for implementation simplicity: it lives entirely in this repo and doesn't require touching `ops-tech`'s nginx sidecar or adding a CDN. If cache-sharing across replicas or surviving restarts ever matters, that's a different, bigger change (nginx `proxy_cache` or a CDN in front of the ALB), not a tweak to this module.
- Call sites still keep their existing try/catch-to-empty-fallback pattern; `cachedFetchJson()` returns `null` on a non-OK response instead of throwing, so a call site's old `if (res.ok) {...}` check becomes `if (json) {...}` (or `json?.data ?? []`).

## Wiring a homepage section to Strapi ("套版")

When asked to wire an unwired section to a named Strapi field (e.g. "前台:科技生活 / 後台:首頁設定 s_4_2s 補資料"), the field lives on the `index-page` single type and the naming convention is `s<section number>_<sub-index>` (e.g. `s4_1`, `s_4_2s`, `s9_2_tech_titan`) — matches the section's position in the Figma/CMS "首頁設定" (homepage settings) admin page, not the component's file name. Confirm the mapping by title text (e.g. grep the component for its Chinese `<p>` heading), not by guessing from the field name alone.

1. **Discover the field's shape before writing any fetch code.** The Content API token in `.env` usually can't reach `/api/content-type-builder/...` (403, admin-only), and blind `populate` guesses either 400 (`Invalid key`) or silently no-op — so use the **`fields` probe**: `GET /api/index-page?populate[<field>][fields][0]=<guess>` returns a `ValidationError: Invalid key <guess>` for a name that isn't a real attribute, and no error for one that is. Loop through candidate names (start with the `news_*` set already used elsewhere: `news_title`, `news_category`, `news_content_html`, `news_featured_image_url`, `news_published_at`, `news_article_url`, `news_youtube_id`) to map out the real schema instead of trial-and-erroring the component code itself.
   - If the field is a **direct relation** (not a nested component), a populated array item comes back as a flat object with its own `id`/`documentId` plus the `news_*` fields directly — no `__component` wrapper (compare to a dynamic zone item, which has `__component: "shared.article-block"` and needs `populate[field][on][shared.article-block][populate]=...`, and errors with `"Using fragments is not permitted"` if you try that `on` syntax on a plain relation).
   - A bare `populate[<field>]=true` is enough to fetch a relation's own scalar fields; no nested `populate` key is needed unless the related entry itself has further relations to expand.
2. **Write the component** following the existing pattern (see `Crossover.astro` / `Tech.astro`): fetch in frontmatter wrapped in try/catch → empty array on failure, map the raw response into a small local `interface` (mirrors `news_*` fields), replace the hardcoded `<li>` markup with `{cards.map(...)}`. Keep the same `target="_blank" rel="noopener noreferrer"` external-link convention as `Hero.astro`'s `.newslist`. Do **not** keep a hardcoded-list fallback for the array itself (unlike scalar title fields, which do fall back to a static default) — an empty CMS field should render an empty list, matching `Video.astro`/`New.astro`.
3. **Filling the actual data ("補資料") is a content-manager relation-picker task, not an API call** — the Content API token only ever had `find` permission during this project, never `update` (`PUT /api/index-page` returns 403). Do it via `claude-in-chrome` against `{STRAPI_URL replaced with the admin.* host}/admin/content-manager/single-types/api::index-page.index-page` — if the user's browser already has an admin session open, no extra credentials are needed. In that page, each Strapi-relation field renders as an "Add or create a relation" combobox:
   - Typing filters the picker, but the search seems to require ~3+ characters and sometimes only matches some indexed field — a query that "should" match by substring can return "No relations available" for no obvious reason. If a Chinese-keyword search comes up empty, retry with a distinctive English substring from the same title (or vice versa) before concluding the article isn't in the library.
   - **After selecting an item, the list re-renders and re-flows — never chain a second blind click at the same coordinate without a fresh screenshot in between.** Clicking stale coordinates from a screenshot taken before the previous selection can land on a completely different row (a 🔗 icon opens a full-page "Edit a relation" modal for *that* unrelated entry, and any further typing goes into whatever field is focused inside it — e.g. silently corrupting `news_article_id` on an unrelated article). If this happens, close the modal via the confirmation dialog's "Confirm" (discard), never "Save" — Strapi warns "changes were not saved" and closing without saving reverts it, so nothing is corrupted as long as you don't click that field's Save button.
   - Save via the single type's own "Save" button (top right "ENTRY" panel). This project's `index-page` has no separate Draft/Publish step for this content — Save alone makes it live (verify with a plain `GET` on the Content API afterward).

## Dynamic routes ([category].astro, [category]/[id].astro, experts/[slug].astro)

- **Never add `export const prerender = true` to a dynamic route that fetches Strapi in its frontmatter.** Prerendering moves that fetch to build time, and the Docker build stage doesn't have `STRAPI_URL`/`STRAPI_API_TOKEN` (K8s only injects them into the container at start, after the image is already built) — `pnpm build` fails with `EnvInvalidVariables: STRAPI_URL is missing`. All three dynamic routes are plain SSR reading `Astro.params` directly at request time instead (`experts/[slug].astro`'s frontmatter comment has the full incident writeup, from when this was tried and reverted).
- For a route that can't resolve its data (bad category/id/slug), guard with `if (!expert) return Astro.rewrite('/404');` rather than letting the page render with undefined props — see `experts/[slug].astro`/`[category].astro`/`[category]/[id].astro` for the pattern, backed by `src/pages/404.astro`.

## Hover conventions

Hover treatments follow the Figma handoff's component specs (`newsRow` and `card/latestNews` etc. in the "Handoff: TVBS TECH Website Design" file) rather than ad-hoc per-section choices. Two shared patterns are established — reuse them instead of inventing new hover language:

- **List rows** (date/time + thumbnail `.img` + `.titleBox` + arrow, e.g. `.newslist` in `global.css` used by Hero/Crossover/Tech, and `#category .list`): on hover, the thumbnail gets a `rgba(0,0,0,0.2)` overlay via `.img::after`, and `.titleBox` fades to `opacity: 0.6`. Date and arrow are untouched.
- **Image cards with a corner reveal button** (e.g. EditorPick's "影響 AI 的十件事" cards, New.astro's scrollytelling cards): on hover, the image gets the same `rgba(0,0,0,0.2)` `::after` overlay, and a 60×60 white/blue-bordered arrow button (`.cardArraw`, reusing `/arraw-right-01.svg`) slides in from just outside the corner (`right/bottom: -60px` → `0`) — the same off-canvas-slide-in mechanic as the pre-existing shared `.statusIcon` component in `global.css`, just sized/bordered differently per that Figma component.
- If a card's clickable root isn't already an `<a>` (e.g. New.astro's `.item` was a plain `<div>`), wrap the content in `<a class="cardLink">` with `display: contents` so the anchor becomes clickable/hoverable without needing to rewrite the existing child layout CSS. Any nested `<a>` tags (e.g. tag chips) must be converted to non-anchor elements first — `<a>` cannot nest inside `<a>`.
- Don't assume a hover effect belongs somewhere just because a visually similar block elsewhere has one — confirm against the actual Figma node for that component before adding it (e.g. `#video`'s scattered mosaic list intentionally keeps its own bespoke hover — image scale + title reveal — instead of the list-row pattern above, and its play-icon button was deliberately left as the pre-existing unbordered `.statusIcon`, not resized to match the card pattern).

## CSS minification gotcha: backdrop-filter pairs

When a rule declares both `backdrop-filter: blur(Npx)` and `-webkit-backdrop-filter: blur(Npx)` with the identical value (e.g. `header.css`'s `.navBlur`/`.subMenu`, `article/adult.css`'s `#adult`), `pnpm build`'s CSS minifier treats them as duplicate declarations and silently keeps only whichever is declared **last** in source order, dropping the other. `pnpm dev` doesn't minify, so this never shows up locally — only after a real build/deploy, which makes it look like a deploy/environment bug ("works on localhost, missing on the live site") rather than a source-order issue. Always declare `-webkit-backdrop-filter` first and the standard `backdrop-filter` last in these pairs, since current Chrome/Firefox don't honor a bare `-webkit-backdrop-filter` with no unprefixed fallback. To verify a blur effect actually survived a build: `pnpm build` then `grep -RoE "backdrop-filter:[^;]*;" dist/client/_astro/*.css` (or fetch the deployed `_astro/*.css` bundle directly) rather than assuming it's a deploy/CDN issue.

## Collaboration form backend (Google Apps Script)

The "與我們合作" form in `Partners.astro` POSTs to a hardcoded `COLLAB_FORM_ENDPOINT` URL (in that component's inline `<script>`) pointing at a Google Apps Script Web App deployment — there's no first-party API for it. The Apps Script project (`TVBS TECH 合作表單通知`) has several independent deployments under 部署 → 管理部署作業, each with its own deployment ID/URL and its own pinned code version, plus unrelated Library-type deployments that are *not* what the site calls. Editing the script and clicking "新增部署作業" (new deployment) creates a different deployment/URL and does nothing for the live one. When a change to the Apps Script isn't showing up on the live site: open 管理部署作業, find the deployment whose ID matches the `AKfycbyy...` URL hardcoded in `Partners.astro` (match by ID, not by label — a deployment named e.g. "v1 - 官網合作表單通知" can be an unrelated Library deployment), then use its pencil/edit icon → 版本 dropdown → 建立新版本 → 部署 to point that specific deployment at the latest code.

## Fonts

Fonts are loaded via `@fontsource` packages (`@fontsource/noto-sans-tc`, `@fontsource/roboto`, `@fontsource/roboto-flex`) and imported per-weight in `global.css`, e.g. `@import '@fontsource/noto-sans-tc/400.css';`. When adding new font weights/styles, import the specific weight file rather than the whole package.
